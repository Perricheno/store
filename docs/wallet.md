# Денежный баланс покупателя

Баланс хранится в целых тенге (KZT). Новый кошелёк имеет нулевой баланс. Средства поступают только после подтверждения оплаченного счёта пополнения; административного начисления нет. Демо-режим использует ту же бухгалтерскую цепочку с mock-счётами и явно не представляет реальные деньги.

Кошельки разделены по `(user_id, environment)`: `mock`, `sandbox` и `production` не обмениваются средствами. Доступ имеет только вошедший покупатель, сменивший временный пароль. Email, visitor ID или токен заказа не дают доступа к чужому кошельку.

`wallet_entries` — неизменяемый журнал; триггер БД запрещает UPDATE и DELETE. Проводки `topup_credit`, `order_debit`, `order_refund`, `topup_reversal` изменяют проекцию `wallets.balance` в одной транзакции. Уникальные индексы запрещают повторное зачисление пополнения, списание заказа и возврат заказа. Сумма кредитов минус дебеты должна равняться balance. Возврат заказа возвращает деньги исходному владельцу и окружению; физический товар автоматически на склад не возвращается.

## API

- `GET /api/wallet`: баланс, среда, блокировка, доступность пополнения, последние 100 проводок и пополнений.
- `POST /api/wallet/topups`: `{amount, phone, idempotencyKey}`. Сумма 1–100000000 целых тенге; одинаковый ключ с другими параметрами отклоняется.
- `GET /api/wallet/topups/:id`: собственное пополнение текущего окружения.
- `POST /api/wallet/topups/:id/simulate`: только собственный mock-счёт вне production. Проходит через запись invoice и обработчик paid; прямого изменения balance нет.
- `POST /api/checkout`: существующий контракт плюс `paymentMethod: "apipay" | "wallet"`, по умолчанию `apipay`. Wallet требует customer-сессию. Цена, остатки, списание, оплаченный заказ и очистка корзины фиксируются одной транзакцией.
- `POST /api/staff/orders/:id/wallet-refund`: полный идемпотентный возврат wallet-заказа; manager/owner после смены временного пароля.

Worker обрабатывает `create_wallet_topup_invoice`, сохраняет invoice и периодически сверяет известные счета. Подписанный webhook сопоставляется только с заранее созданным пополнением. Проверяются invoice, исходная сумма и среда. Повторы webhook и polling не создают повторных проводок. Существующий внешний платёж заказа остается отдельной сущностью; wallet-заказы не выставляют счет ApiPay.

## Возврат пополнения и блокировки

Подтвержденный полный возврат пополнения списывает ранее зачисленную сумму отдельной проводкой, если средств достаточно. Если возврат предшествует paid, поздний paid не зачисляет деньги. Если средства уже потрачены, отрицательный баланс запрещен: кошелек блокируется, пополнение получает `manual_review`, событие сохраняется с `resolved=false`; повторная сверка продолжает рассматривать долг. Сумма фактических реверсов проверяется по журналу, поэтому повторное уведомление не списывает деньги дважды.

Частичный возврат требует ручной проверки. Когда известна целая накопленная сумма `invoice.total_refunded`, доступные средства списываются точно до этой суммы; при отсутствующей/дробной сумме деньги не угадываются. Кошелек остается заблокированным до операционного разбора. Автоматической разблокировки, ручной выдачи денег и инструментов обхода задолженности нет. Не считать `manual_review`/`resolved=false` завершенным финансовым урегулированием. Проверять эти строки напрямую через защищенные операции БД; не редактировать журнал.

## Подключение реального режима

Production-пополнение и оплата с баланса выключены по умолчанию (`WALLET_PRODUCTION_ENABLED=false`). До включения необходимо согласовать с мерчантом и провайдером именно сценарий покупательского баланса, настроить `APIPAY_MODE=production`, API key, webhook secret, доступный webhook и работающий worker. Само наличие invoice API не подтверждает договорную допустимость кошелька. В sandbox нужны key/secret соответствующего окружения; производственный флаг не нужен. Реальные ключи не хранить в репозитории.

Первичный источник: [документация ApiPay](https://apipay.kz/apipay-api-docs.md), разделы `POST /invoices`, `GET /invoices/{id}`, `invoice.refunded` и `Signature Verification`. Телефонные счета принимают целые тенге, описание ограничено 60 символами. `external_order_id_idempotency` уникален внутри организации (до 191 символа); провайдер может перевыставить счет с тем же ключом после expired/cancelled/error. Используются собственные UUID сущностей. Уведомления возврата проверяются только при `refund.status=completed`; неизвестный исход не считается возвратом.

## Текущие операционные ограничения

Сверка пополнений читает до 50 известных незакрытых счетов за проход, включая историю, с ротацией по времени последней проверки. При большой истории это увеличивает задержку обнаружения пропущенных уведомлений; отдельная приоритетная очередь и мониторинг требуют дальнейшего развития. Подтвержденный статус `error` при чтении провайдера также сохраняется, даже если webhook потерян.

Блокировки и финансовые случаи `manual_review` пока разбираются только через защищенные операции БД; штатного интерфейса безопасного урегулирования и разблокировки нет. Это операционный пробел, а не готовность к производственной эксплуатации. Production-флаг должен оставаться выключенным до согласования бизнес-сценария и утверждения процесса урегулирования.
